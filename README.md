## 3. Charter

- **Судлах:** Ном нэмэх, хайх, устгах болон API үйлдлүүд.
- **Ашиглах:** Хоосон оролт, буруу өгөгдөл, том/жижиг үсгээр хайх болон API хүсэлтүүд.
- **Илрүүлэх:** Оролтын баталгаажуулалт, хайлт, өгөгдлийн бүрэн бүтэн байдал, алдааны мессеж болон API хариултын согогууд.

### Сонгосон аялалууд

1. **Supermodel (GUI):** Хуудасны талбар, товч, мессеж болон хүснэгтийг шалгах.
2. **Couch Potato:** Хоосон болон дутуу оролтоор баталгаажуулалтыг шалгах.
3. **Saboteur:** Буруу өгөгдөлтэй API хүсэлт илгээж шалгах.
4. **Fed-Ex:** Ном нэмэх, хайх, устгах үед өгөгдөл зөв дамжиж байгаа эсэхийг шалгах.

## 4. Туршилтын үр дүн

Туршилтын явцад дараах боломжит согогуудыг ажиглаж, тайлан бэлтгэв.

- `/old` хуучин хувилбарын хуудас Internal Server Error буцаасныг тэмдэглэсэн.

Согог тус бүрийн дэлгэрэнгүй мэдээллийг `bugs/` хавтаснаас үзнэ үү.

## Дүгнэлт (Debrief)

### 1. Аль аялал хамгийн үр дүнтэй байсан бэ?

Туршилтын үеэр Supermodel, Couch Potato, Saboteur болон Fed-Ex гэсэн дөрвөн аяллын дагуу “Уншлагын жагсаалт” веб системийг шалгасан. Supermodel аяллаар системийн үндсэн үйлдлүүд, хайлт болон хэрэглэгчид харагдах мэдэгдлүүдтэй холбоотой алдаанууд илэрсэн. Couch Potato аяллаар хоосон талбар болон буруу форматтай он оруулахад ном нэмэгдэж байгаатай холбоотой асуудлууд илэрсэн. Fed-Ex аяллаар номын жагсаалт, хайлтын үр дүн болон нийт номын тоо хоорондоо зөрж байгааг илрүүлсэн. Saboteur аяллаар буруу болон дутуу API хүсэлт, байхгүй номын ID, HTML тусгай тэмдэгтийн дүрслэлтэй холбоотой асуудлууд илэрсэн. Иймээс хэвийн бус оролт болон алдаатай нөхцөлийг шалгах зорилгоор Saboteur аялал үр дүнтэй байсан бол бусад аяллууд үндсэн үйлдэл болон өгөгдлийн нийцлийг шалгахад тусалсан.

### 2. Charter-аас гадуур ямар асуудал илэрсэн бэ?

Туршилтын явцад `/old` замд хандахад `Internal Server Error` гарах, байхгүй номын ID-аар DELETE хүсэлт илгээхэд `200 OK` буцах, дутуу мэдээлэлтэй POST хүсэлтэд `201 Created` буцах зэрэг асуудлыг шалгасан. Мөн HTML тусгай тэмдэгт оруулахад интерфейс дээр хэрхэн дүрслэгдэж байгааг ажигласан. Эдгээр шалгалт нь хэрэглэгчийн интерфейсээс гадна API-ийн хариу болон серверийн үйлдлийг судлахад тусалсан. Гэхдээ HTTP амжилттай төлөв буцаасан нь тухайн үйлдэл бизнес логикийн хувьд зөв ажилласныг дангаараа батлахгүй. Дараагийн session-д API-ийн хариу, өгөгдлийн өөрчлөлт болон интерфейс дээр харагдах үр дүнг хооронд нь тулган шалгах шаардлагатай.

### 3. Аль алдааг автомат тестээр илрүүлэх боломжтой байсан бэ?

Энэ session-д Playwright ашиглаагүй. Веб интерфейсийг Google Chrome дээр гараар шалгаж, API-ийн зарим үйлдлийг `curl.exe` ашиглан туршсан. BUG-01, BUG-04 зэрэг оролтын баталгаажуулалтын асуудал, BUG-02, BUG-03 зэрэг жагсаалт ба статистикийн зөрүү, BUG-06, BUG-09 зэрэг буруу мэдэгдлийг автомат UI тестээр шалгах боломжтой. BUG-10, BUG-11 зэрэг API-ийн хариу болон HTTP статусын асуудлыг автомат API тестээр илрүүлж болно. BUG-07 хайлтын том, жижиг үсгийн ялгаа болон BUG-05 замын хариуг мөн автомат шалгалтаар туршиж болно. Харин BUG-08 шиг харагдах байдлын асуудлыг гараар шалгах эсвэл visual regression тест ашиглан илрүүлэх боломжтой. BUG-12-ын хувьд DOM-д хадгалагдаж буй текст болон хэрэглэгчид харагдах дүрслэлийг тус тусад нь шалгах хэрэгтэй. Автомат тест нь давтагддаг шалгалтад тустай боловч exploratory testing-ийг бүрэн орлохгүй.

### 5. Юу шалгагдаагүй үлдсэн бэ?

Энэ session-д автомат браузерын тест, олон хөтөчийн нийцэл, өөр өөр дэлгэцийн хэмжээний визуал нийцэл болон давтан автомат гүйцэтгэлийг шалгаагүй. Мөн хүснэгтэд дурдсан бүх нэмэлт нөхцөл, бүх хил хязгаарын утга, олон хүсэлт зэрэгцэн ирэх үеийн ажиллагааг бүрэн хамарсан гэж үзэхгүй. Дараагийн session-д өмнө илэрсэн согогууд засагдсан эсэхийг дахин шалгаж, хамрагдаагүй нөхцөлүүдэд зориулсан шинэ charter боловсруулна. Давтагддаг шалгалтуудаас эхлэн автомат тест нэвтрүүлэх боломжийг мөн судална.


### Ерөнхий дүгнэлт

Энэхүү session-ийн үр дүнд системийн үндсэн үйлдлүүдийг шалгахаас гадна хэвийн бус оролт, API-ийн хариу үйлдэл болон өгөгдлийн нийцэлтэй холбоотой асуудлуудыг судалсан. Илэрсэн асуудлуудыг тус тусад нь баримтжуулж, шаардлагатай тохиолдолд нотлох зураг болон командын үр дүнгээр баталгаажуулсан. Туршилт нь зөвхөн системийг зөв ашиглах нөхцөлийг шалгах бус, харин буруу оролт болон урьдчилан тооцоолоогүй нөхцөлд хэрхэн ажиллаж байгааг судлахын ач холбогдлыг харуулсан. Дараагийн session-д өмнөх асуудлууд засагдсан эсэхийг дахин шалгах, API-ийн хариу болон интерфейсийн үр дүнг тулгах, мөн давтагддаг шалгалтуудад автомат тест нэвтрүүлэх боломжийг судлах шаардлагатай.
